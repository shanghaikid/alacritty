# OSC 7501 implementation and acceptance

Target: [Program Status Protocol revision 0.4](https://www.superlogical.com/rex/docs/build/program-status).

This work covers the installed Alacritty fork and the user's tmux workflow.
The shared `alacritty_status` crate owns parsing and record semantics so both
receivers use identical validation and lifetimes.

## Required behavior

- Both terminators, chunked input, feature queries and fixed capability replies.
- All five states, clearing, optional fields, duplicates, unknown/malformed
  pairs, strict UTF-8/base64 and decoded-control rejection.
- Independent root and child records, complete replacement, nearest-ancestor
  app inheritance, segment-aware subtree clearing and least-recently-updated
  eviction at the documented 64-record cap.
- Preserve records across alternate screens and soft resets; clear on RIS;
  expire transient records on process exit and OSC 133 A; retain done/error.
- Plain, bounded status labels that retain the host window/pane identity and
  strip invisible directional/formatting controls before display.
- Enforce wire and field limits before allocation or mutation, including
  overlong/unterminated sequences at the streaming parser layer.
- No record contents in terminal replies; query replies contain constants only.
- Native window/tab status and per-pane tmux status with unchanged normal
  terminal text, theme, shortcuts and the existing IME fix.

## Performance acceptance

- No work in the normal printable-text fast path beyond the existing parser.
- Lazy storage; fixed decoded-text scratch buffers; bounded retained memory.
- Zero heap allocations for warmed duplicate reports, progress-only updates,
  invalid input and capability detection in the shared engine.
- Exact duplicate packets avoid reparsing and base64 decoding. Existing strings
  reuse their allocations; record lookup caches the last writer.
- Coalesce status changes at PTY-read/UI boundaries. Duplicate reports cause
  no UI update; status display is throttled with demand-driven one-shot
  scheduling rather than polling or per-report subprocesses.
- Benchmark duplicate, progress, maximum record sets, text/base64, malformed,
  overlimit, query and end-to-end terminal workloads. Compare normal-output
  throughput against the pre-change parser with repeat samples. Record actual
  timings, allocation counts, memory limits and UI update counts before claiming
  performance acceptance.

## Usage

Programs must emit the protocol themselves; existing applications are not
inferred from titles or screen contents. No extra Alacritty setting is needed.

```sh
printf '\033]7501;state=working:app=build:progress=42\033\\'
printf '\033]7501;state=blocked:kind=permission:app=build\033\\'
printf '\033]7501;state=done:app=build\033\\'
printf '\033]7501;state=clear\033\\'
```

The native window/tab retains its normal title and adds e.g.
` — [working 42%] build`. The most actionable record wins, with recency
breaking ties: blocked, error, done, working, idle. Title text, then inherited
app, then message supplies its label. The label is bounded to 96 characters
and strips directional and invisible formatting controls. No notifications,
sounds, polling, shell processes or git commands are triggered by reports.

Ordinary tmux consumes unknown OSCs. For **raw reports inside tmux**, build
[our tmux fork's osc7501 branch](https://github.com/shanghaikid/tmux/tree/osc7501)
with `contrib/program-status/build.sh`; add `#{pane_program_status}` to its
status format. It uses this same Rust engine through a static C ABI, with
one store per pane and at most one 100 ms status timer per pane. tmux displays
only fixed state/kind/progress text, so application strings cannot inject
format markup. The pane's existing directory/branch label remains visible.

Replacing an executable does not replace an already-running tmux server.
Existing sessions are preserved during installation. Use a separate server
(e.g. `tmux -L osc7501 new-session -A -s alacritty`) to try the new build now;
a default server uses the new executable after its old sessions exit.

For diagnostics, `alacritty msg program-status` reads the **local administrative
IPC socket**, just like `get-config`; `--window-id=-1` lists all windows.
It includes record snapshots and native title update counts. This is not a
terminal escape sequence: PTY queries always return constant capabilities,
never stored ids, messages or titles. A shell connected to the PTY cannot use
OSC 7501 to read records.

## Measured performance (Apple Silicon, release build)

`cargo bench --locked -p alacritty_status --bench status`, one million updates
per case after warmup, counted both allocations and reallocations:

| Case | ns/report | Heap allocations |
| --- | ---: | ---: |
| Exact duplicate | 19.4 | 0 |
| Progress change | 116.9 | 0 |
| 64 round-robin writers | 219.8 | 0 |
| Maximum decoded message | 6686.2 | 0 |
| Invalid base64 | 46.4 | 0 |
| Over wire limit | 1.8 | 0 |
| Capability query | 2.6 | 0 |

The store is 2328 bytes before its first record. Record count is capped at 64;
individual strings and the last-packet cache have protocol-bounded capacities.
The streaming parser retains at most 4092 raw report bytes (4096 capacity),
even when fed a 4 MiB unterminated report. Oversized reports are discarded
whole; OSC 52 clipboard handling retains its existing independent behavior.

Seven alternating before/after samples using `alacritty_terminal/examples/throughput.rs`:

| Full terminal workload | Before MB/s | After MB/s |
| --- | ---: | ---: |
| Ordinary text | 169.55 | 170.40 |
| Text with ANSI attributes | 112.41 | 110.60 |

Ordinary text is unchanged within run variability; the ANSI workload measured
1.6% lower. The parser-only microbenchmark measured 1121.91 → 1119.81 MB/s
for ASCII, 655.16 → 627.87 MB/s for ANSI, and 422.95 → 990.54 MB/s for status
sequences (upstream only discards those). These are measured tradeoffs, not a
claim of mathematically optimal throughput. Payload runs use bulk bounded
copies; the normal printable-text path does no status decoding or allocation.

Native PTY acceptance sent 50,000 changing reports in 0.143 seconds and saw
only two native title updates. Another 50,000 duplicate reports caused zero
title updates. Unit tests exercise 100,000 changes while the UI is stalled
and assert exactly one queued event. Neither report workload dirties the grid.
All status display updates, including state transitions, are limited to 10 Hz
with a single demand-driven timer, and the final update is always delivered.

## Validation

```sh
cargo test --locked --workspace
cargo bench --locked -p alacritty_status --bench status
python3 extra/program-status-acceptance.py target/release/osx/Alacritty.app/Contents/MacOS/alacritty
```

The native acceptance script creates and terminates only its own isolated
window/child process and never sends input to existing terminals.

## Completion evidence

The workspace suite passes: 84 application tests, 132 terminal unit tests,
12 record-engine tests, 3 protocol integration tests, 45 terminal reference
tests and configuration/doc tests. The vte fork passes 59 tests with std/ansi,
and its no-std/ansi suite passes too. Streaming tests include every report
split boundary, cancelled/malformed terminators, exact wire limits, clipboard
regressions and bounded unterminated input. Ordinary fragmented UTF-8/CSI/ESC
output retains its normal wakeup. Native acceptance also covers synchronized
output ending by timeout, without a later PTY write.

The tmux acceptance suite checks both capability replies, actual attached
client rendering, hierarchy/clearing, primary/alternate screens, soft/full
resets, prompt/process-exit lifetimes and invalid/cancelled reports. A 32 MB
oversized report changed server RSS by at most 16 KiB in measured runs.
Alacritty and tmux use pinned remote sources and can build independently;
installation records and binary hashes are retained in the local backup
manifest. Existing tmux servers are intentionally preserved and need a new
server process to use the replacement binary.
